# Audit Workflow (GLM hub-spoke)

You are the Claude HUB. Do NOT use `ultracode` / Claude-heavy Workflow orchestration for these items — the orchestration now routes VOLUME to GLM `glm-code` spokes and EXTERNAL RESEARCH to agy (`/research`), keeping Claude for judgment only. For each item: the hub decomposes it into a spec, fires GLM spoke(s) to find → verify → fix → test, then the diffs get read and the gates get run by reviewer/verifier subagents and the hub issues the verdict on their evidence.

**Binding for this whole document:** wherever a step below says "hub reviews" / "hub verifies" / "hub runs the gates" / "hub maps" / "hub reads" / "hub specs out", that means the hub DELEGATES the reading and running to a `code-reviewer` / `security-reviewer` / `design-reviewer` / `verifier` subagent and then decides on the returned evidence. The hub itself executes nothing, however small (never-work-hub-side rule, `~/.claude/OPUSPLAN.md`). Any external-fact lookup (CVE, version, advisory, license) goes to agy via `/research` — the hub does not web-search directly.

Read `~/.claude/orchestrator/PROTOCOL.md` once before starting (adjust the path if your hub-spoke orchestrator lives elsewhere). Queue these IN THIS ORDER and autonomously finish each (findings + fixes + tests, hub-verified) before starting the next. Use `audit.md` at the repo root to speed up (create if missing: what was audited when, known-clean areas, recurring hotspots, commands/gates used).

**Step 0: Project Profile (runs FIRST — before item 0 and every item below; supersedes the old standalone public-facing gate, which is now the Exposure dimension).** The whole audit is conditional on what this project actually is: a personal, local-only tool is not audited as if it were a payment-handling public SaaS. Derive the profile from evidence in the repo, write it to the TOP of `audit.md` under `## Project profile (<date>)`, and gate every item against it. Each dimension records **the evidence that decided it** (file:line, or the command + its output), not just the verdict — no evidence found → record `unknown`, never a guess. Delegate the derivation to a `verifier` subagent (never hub-side). On later runs, reuse the recorded profile rather than re-deriving it, and only re-derive if the repo changed materially since that date (new deploy/hosting config, auth provider added or removed, a payment SDK added, new schema tables or columns, repo visibility flipped, first real users).
   - **Exposure** — local-only / internal / public-facing. Signals: deploy config present (`vercel.json`, `Dockerfile` with published ports, `fly.toml`, a CI deploy job), a registered domain in config or README, host binding (`127.0.0.1` vs `0.0.0.0`), an auth provider present, the README's own self-description.
   - **Repo visibility** — public / private. Detected separately from exposure, and independent of it: a public repo leaks secrets whether or not the app is deployed. `git remote -v`, then `gh repo view --json visibility` if a remote exists; no remote → private.
   - **Users**: none (single operator) / known small group / open signup / enterprise B2B. Signals: a signup route, an invite flow, auth-provider config, a user table, enterprise procurement or contract templates.
   - **Data sensitivity** — synthetic-or-none / personal data / special-category (health, financial, government ID, biometric, children). Signals: schema column names (`email`, `phone`, `dob`, `national_id`, `iqama`, `diagnosis`, `mrn`, `card`, `iban`), file uploads, third-party health/finance SDKs.
   - **Money** — none / payments / marketplace-or-payouts. Signals: a Stripe/Paddle/Tap/Moyasar/PayPal SDK, a checkout route, a webhook handler, payout or KYC code.
   - **Client surfaces** — single web deploy / mobile app-store build / public or third-party-consumed API. Signals: `ios/`+`android/` dirs, Expo/Capacitor config, a published OpenAPI spec, API-key issuance code. (This dimension gates item 14: AI-assistant discoverability / llms.txt applies only when a public web-facing site exists.)
   - **Persistence** — none / DB / user-generated content. Signals: an ORM/schema/`migrations/` dir, storage-bucket config.
   - **Async** — synchronous only / jobs, queues or webhooks present. Signals: a queue library, cron config, `/api/webhooks` routes, a worker entrypoint.
   - **Third-party in request path** — yes / no. Signals: outbound SDK calls (LLM, email, payments, storage) inside route handlers.
   - **Runtime** — long-lived server / serverless-or-edge. Signals: framework + host config.
   - **Stage**: pre-launch (seed data only) / live users / seeking external financing. Signals: production env config, analytics wiring, real user rows if the DB is actually inspectable, README or vault note status line, pitch deck or grant/loan application files. **This is the weakest dimension (none of those prove live users)**; if it stays ambiguous record `unknown`, treat as pre-launch, and say so in the report rather than inventing a user base.
   - **Jurisdiction** — none stated / GDPR / KSA PDPL / other. Signals: privacy-policy text, target market in README or the vault project note, currency and locale config, Arabic/RTL support.

   **Ambiguity rule:** infer the most likely value and record a confidence (high/medium/low) — the audit resolves ambiguity autonomously and does NOT interrogate the user over minor dimensions. Exactly three dimensions may stop the run for a one-line question, and only when the ambiguity flips an entire class of checks: **exposure, money, data sensitivity**. Everything else is decided from evidence or marked `unknown`. Record any answer in `audit.md` so re-runs don't re-ask.

   **Verify skill:** if the profile shows a user-facing UI, ensure verify skill per PROTOCOL (Standing loop order, step 0) before item 1; use it for every live UI check below.

**ALWAYS-ON floor — the only unconditional checks in this document.** Deliberately short and closed: these four run on EVERY project whatever the profile says, because their blast radius doesn't depend on exposure, users, money or stage.
   - **Secrets committed or present in git history** — a repo that is public, or ever becomes public, leaks them with nothing deployed; rotation is the fix, not deletion.
   - **Hardcoded credentials in source** — same leak, and they travel with every clone, fork and backup.
   - **Destructive data-loss bugs** (unscoped `DELETE`/`UPDATE`, a wipe path, a migration that drops data) — destroys the operator's own data with no attacker and no audience required.
   - **Malicious or known-compromised dependencies** (typosquats, hijacked packages, install-time scripts) — they execute on the developer's own machine at install. Distinct from ordinary CVE triage in item 4, which IS exposure-gated.

   Nothing else below is unconditional. Every other check runs only if the profile shows its trigger present, and a check whose trigger is absent is reported as `N/A — <trigger absent>`, never as a finding, gap or debt item.

0. **Idea pressure-test (hub-run, judgment task — not spoke-delegated). Gate: the project is meant to be a product — money ≠ none, OR users ≠ none, OR exposure = public-facing, OR the README/vault note frames it as a venture. A personal single-operator tool with no users and no money has no "startup idea" to pressure-test → `N/A — not a product`.** Before auditing the code, pressure-test whether the underlying idea/direction still holds, using this exact frame:

   > **Role:** act as a Paul Graham-style startup evaluator who has reviewed thousands of ideas and knows exactly which ones die in week one and which become billion-dollar companies.
   > **Task:** pressure-test the idea the way Paul Graham evaluates YC applications — find every fatal flaw before wasting a month building the wrong thing.
   > **Steps:** (1) state the startup idea being tested; (2) identify the core assumption that must be true for the business to work; (3) find the three most likely reasons this idea fails — specific, not generic; (4) test the problem — is this a real pain people pay to solve, or a nice-to-have; (5) assess founder-market fit — why is this founder the right person to build this; (6) deliver a brutally honest verdict — STRONG, WEAK, or PIVOT REQUIRED.
   > **Rules:** every flaw must be specific to this idea, not generic startup advice; the core assumption must be testable before building anything; the verdict must be direct, never "it has potential but"; fatal flaws ranked by severity, most dangerous first; test: would Paul Graham fund this in its current form.
   > **Output shape:** core assumption → three fatal flaws → problem validation → founder-market fit → brutal verdict.

   Write findings to `idea-pressure-test.md` (gitignored) before acting on them. Loop per the rule below: WEAK verdicts with addressable flaws get mitigated (plan/doc changes, scope cuts) and re-tested until a pass returns STRONG or the remaining flaws are genuinely structural. A **PIVOT REQUIRED** verdict is a decision only the user can make — stop the loop, report the verdict and reasoning, and wait for direction rather than pivoting autonomously.

Hub specs a bug hunt; GLM spokes hunt across the whole codebase and VERIFY each finding, writing `bugs.md` (gitignored) BEFORE any fix; then spokes fix + test each; hub reviews every diff and runs the gates. 2. **Security (gate: the scanner layer is ALWAYS-ON — it is how the floor's secrets/credentials/malicious-dependency checks are actually executed. The spoke business-logic layer below is gated per the gate map.)** — run the free deterministic scanners FIRST via a `verifier`/haiku subagent (cheap, zero GLM quota, and never hub-side per the never-work-hub-side rule): `semgrep scan --config auto`, `gitleaks detect`, `osv-scanner scan .` (or `trivy fs .` if IaC/containers present — OSV-Scanner doesn't cover IaC). If a scanner is missing locally (`command -v`), note it in `audit.md` and continue — don't silently skip the layer on the next repo too.

   **Backend-reachability checklist — profile-gated per the gate map below, NOT blanket.** Learned 2026-07-31 from a `/watch` teardown of @millee.md "Securitymaxxing knowledge (vibecode edition)". The gate question per check is *who carries the risk*: audience-load risks (rate limiting, load testing) stay in item 11; anything reachable over the internet by way of a hosted backend belongs HERE — and note that the HOSTED-DATA group below keys on the backend, not on the app's Exposure, because a localhost-only app with a world-readable Supabase table is exposed regardless of whether the app itself is public. Findings go into `secure.md` before any fix, same find-before-fix + loop-until-clean rules as the rest of item 2.

   **Gate map (each bullet inherits its group's gate; a group whose trigger is absent is skipped entirely and its bullets are reported `N/A — <trigger absent>`, excluded from both halves of the score).** A local-only, single-operator, no-auth, no-personal-data tool ends up running only the FLOOR group; a public app with open signup and personal data runs every group. All 40 bullets below belong to exactly one group; if a bullet's group is ever ambiguous, run it — default to the more inclusive reading rather than skipping.
   - **FLOOR (always, no trigger):** secrets/API keys server-side · env files not committed · logs never contain raw secrets · secret scanning as a pre-commit gate (force on repo visibility = public).
   - **HOSTED-DATA (trigger: persistence = DB/UGC on a network-reachable backend, whatever the app's Exposure):** RLS/row-scoped access control · no table public by default · auth-provider↔DB identity actually transmitted (also needs auth) · API server's DB credential subject to RLS · `USING` **and** `WITH CHECK` (both also need RLS to exist) · least-privilege DB credentials.
   - **REACHABLE (trigger: exposure ≠ local-only, or a hosted backend accepts requests from outside the machine):** input validated/sanitized server-side · no stack traces in error responses · admin/debug endpoints locked down · HTTPS end-to-end · routes default-deny across every verb (also needs auth) · security logging (additionally needs users ≠ none — a single-operator tool has no attack population to detect) · explicit request body-size limits on API routes · CORS locked to an explicit origin allowlist · directory listing disabled (N/A on serverless/edge platforms) · upload type whitelist (MIME + extension + magic-byte + size cap) on any user file upload.
   - **AUTH (trigger: an auth system exists at all):** session/token expiry · logout revokes server-side · CSRF on state-changing routes (cookie sessions) · brute-force lockout (also needs exposure ≠ local-only) · password hashing and password-reset link hygiene — both `N/A` when credentials are fully delegated to a third-party provider (Clerk/Auth0/Supabase Auth) rather than self-managed · permission-not-role-name checks and prompt permission-change propagation, both of which additionally need roles/permissions to exist · no user enumeration on auth/signup/reset endpoints.
   - **MULTI-PRINCIPAL (trigger: users ≠ none — more than one identity can hold a session):** object-level ownership / IDOR checks on every resource fetched by a user-supplied id. With users = none there is no second principal to become.
   - **MULTI-TENANT (trigger: a tenancy model is actually modellable — an org/workspace/team table):** roles scoped per organization. Single-tenant → `N/A`, do not recommend building tenancy.
   - **PUBLIC-FORMS (trigger: exposure = public-facing AND an unauthenticated form exists):** bot protection/CAPTCHA on every public form.
   - **AI SURFACE (trigger: an LLM/AI model sits in the request path — user-supplied content reaches a model prompt, or model output reaches users):** prompt injection mitigation · AI usage caps on generation endpoints.
   - **ERASURE (trigger: data sensitivity ≥ personal data AND (exposure = public-facing OR stage = live users)):** data retention and deletion actually implemented · deletion requires step-up reauth and kills every session (also needs auth) · deletion propagates to downstream processors (also needs processors to exist). **Encryption at rest** sits in this group but on the looser trigger of data sensitivity ≥ personal alone — it does not wait for live users. **Store-policy deletion** — self-service in-app account deletion, the public web deletion URL, Apple/Play requirements — additionally requires client surfaces = mobile app-store build; a web-only app skips it.
   - **Secrets and API keys live server-side in env vars**, never hardcoded and never shipped to the client. (Deterministic seed: `gitleaks detect` above, plus grep the client bundle/`NEXT_PUBLIC_*`-style prefixes for anything that isn't meant to be public.)
   - **Env files are not committed.** Verify `.env*` is gitignored AND absent from git history — `git log --all --full-history -- '.env*'` returning commits is a finding, not a clean pass (gitignoring now doesn't unpublish an already-committed key; rotation is the fix, not deletion).
   - **Row-level / row-scoped access control on every table** (e.g. Postgres RLS keyed on `user_id`), not just app-layer checks.
   - **Auth provider and database are separate systems — verify identity is actually transmitted.** An app-layer `if (!user) throw` check proves nothing to the database: the auth provider (Clerk/Auth0/Supabase Auth) and the data layer (Convex/Postgres/Hasura) do not share caller identity by default. Confirm a signed JWT flows between them (auth provider's JWT template wired to the data layer) AND that server functions / RLS policies read identity from that verified token (`ctx.auth.getUserIdentity()`, `auth.uid()`, JWT claims) — not from an app-layer session check the database never sees. Failure mode: query runs under a service/admin credential while the app believes it's scoped to the user.
   - **No table left public by default** — separate check from RLS, different failure mode: RLS *enabled* with a `USING (true)` policy, or a lingering grant to the `anon`/`public` role, is still world-readable. Supabase ships this broken by default. Enumerate every table's policies and role grants; a table with no explicit deny is a finding.
   - **User input validated and sanitized** at every trust boundary (server-side, not just client-side validation — client checks are a UX affordance, not a control).
   - **Upload type whitelist enforced on every user file upload.** MIME type, file extension, AND magic-byte (actual file signature) all validated server-side — not just the client-declared MIME type — plus a size cap per upload. A `.jpg` extension with an `image/jpeg` header proves nothing about the bytes; check the signature.
   - **Error responses don't leak stack traces / internal paths / SQL to the user.** Spoke-audit only — do not assume `semgrep --config auto` catches this; it's intraprocedural and won't trace a handler's error path to the response body.
   - **Admin and debug endpoints are removed or locked down** in production builds (debug routes, `/admin` without auth, GraphQL introspection, verbose health endpoints, framework dev-only panels). Spoke-audit only, same reason.
   - **Security logging exists** — auth failures, authz denials, and rate-limit trips are recorded somewhere durable, so an attack in progress is detectable at all. Absence of logging is itself the finding.
   - **HTTPS enforced end-to-end** — HTTP redirects to HTTPS, cookies marked `Secure`, HSTS set. Added 2026-07-31 from `/watch` teardown of @millee.md "Securitymaxxing knowledge (vibecode edition) pt.3".
   - **Explicit request body-size limits set on every API route**, not left to the platform's implicit default — an unbounded body accepted at the framework layer can still exhaust memory/bandwidth well within whatever cap the host silently applies upstream.
   - **CORS locked to an explicit origin allowlist.** No `Access-Control-Allow-Origin: *` (or a reflected/echoed-origin equivalent) on any route that accepts credentials or returns non-public data; cross-origin access is opened only for the specific origins that actually need it.
   - **Directory listing disabled** on any self-hosted or static-file-serving deployment — confirm the web server / static-file middleware does not auto-index a directory with no index file present. `N/A` on serverless/edge platforms (Vercel, Netlify, Cloudflare Pages) that don't expose a raw filesystem to list.
   - **Passwords stored hashed with a strong algorithm** (scrypt/bcrypt/argon2 — salted, tuned cost factor), never plaintext or reversibly encrypted.
   - **Bot protection (CAPTCHA/challenge) on every public form** — signup, login, contact, newsletter, feedback — not just signup.
   - **Login sessions/tokens expire.** A stolen token that never expires is a permanent backdoor.
   - **Object-level ownership checks on every resource fetched by ID (IDOR / OWASP Broken Access Control, CWE-639).** Added 2026-08-01 from `/watch` teardown of @securedbycasco "Can someone steal your users' data just by pasting a URL?". Distinct from item 3's endpoint auth (that asks *is anyone logged in*) and from RLS above (that only protects queries routed through the DB's row policies): the failure is an *authenticated* user swapping an id in `/api/orders/a8f3e1c9` and reading someone else's row. Enumerate every route/handler that takes a user-supplied identifier (path param, query string, body field) and confirm it re-checks ownership against the session's user server-side. Guessable/sequential ids make it worse but non-guessable ids are NOT the control — absence of an ownership check is the finding even with UUIDs.
   - **Logout actually revokes the session, server-side and client-side.** Added 2026-08-01, same teardown. Distinct from token expiry above: a logout that only redirects leaves the token replayable until it expires on its own. Four client artifacts must be cleared — auth/session cookies, `localStorage`, `sessionStorage`, and any in-memory token — AND the token must be invalidated/revoked server-side (deleted from the session store or added to a denylist) so a replay of the captured token is rejected. Verify by replaying a pre-logout token against a protected route and expecting 401.
   - **CSRF protection on state-changing routes** (cookie-based sessions especially — same-site cookies alone aren't always sufficient).
   - **Password-reset links are single-use and time-limited** — invalidate on first use, expire on a short window, separate check from session expiration above (≤30 min expiry).
   - **Least-privilege database credentials** — the app connects with a DB user scoped to only the tables/operations it needs, never the root/master/admin credential. Distinct from RLS above: this is what limits blast radius if the app's own connection is compromised.
   - **Logs never contain raw secrets** — passwords, session tokens, API keys, card numbers must be redacted/never logged in the first place. Distinct from "security logging exists" above: that check wants logs to exist, this one wants them clean.
   - **Login brute-force lockout, separate from rate limiting.** Failed logins tracked per account AND per IP, with progressive delay or temporary lockout past a threshold — so a slow distributed credential-stuffing run under the global rate limit still trips. Distinct from the endpoint rate-limit item above, which only bounds request volume. Verify by driving repeated bad passwords against one account and confirming lockout fires.
   - **No user enumeration on auth/signup/reset endpoints.** Signup, login, and password-reset responses are identical in content and comparable in timing whether or not the account exists — a distinct "email already registered" vs "no account found" message or a measurable timing gap (e.g. only hashing the password when the account is real) lets an attacker enumerate valid accounts before ever running a credential-stuffing attempt.
   - **Secret scanning runs as a pre-commit gate, not only after the fact.** `gitleaks` (or equivalent) wired into a pre-commit hook / CI push gate so a key never reaches history in the first place — critical on any PUBLIC repo. Distinct from the earlier history-grep check, which only detects reactively. Verify the hook actually blocks a test commit containing a fake key.
   - **Encryption at rest is on and verified, not assumed.** Database, object storage, and backups all encrypted at rest — confirm from the provider's own config output rather than assuming the managed default. Applies with force to health, identity, and payment data.
   - **Data retention and deletion are actually implemented, not just documented.** A user-deletion path really removes or irreversibly anonymizes that user's rows across every table, backups, logs, analytics, and third-party processors, with a documented retention window per data class. Distinct from a privacy policy that only promises it. Verify by deleting a test account and querying for residue. Verification must also catch the pseudonymization trap: confirm the user's surrogate key no longer links them to orders, logs, error traces, search indexes, or analytics — nulling profile columns alone leaves the record re-identifiable and therefore still personal data.
   - **Account deletion is self-service and reachable in-app.** Required by Apple Guideline 5.1.1(v) and Google Play policy for any app with account creation; Play additionally requires a public web deletion URL declared in the Data Safety form. A support-contact-only flow is an App Store rejection. Deactivation is not deletion. Revoke Sign in with Apple / OAuth tokens as part of the flow.
   - **Deletion requires step-up reauthentication and kills every session.** Confirm password/biometric/MFA before accepting the request, then revoke active sessions, refresh tokens, and API keys — otherwise a hijacked session can destroy an account.
   - **Deletion propagates to downstream processors, not just the primary database.** Payment provider, analytics, support desk, email/CRM, CDN and object storage, search index, and cache all need an explicit purge path. Verify by deleting a test account and checking each system for residue.
   - **Authorization checks a permission, not a role name.** Grep for `role === 'admin'` / `role == "admin"` style comparisons in business logic — each is a finding. Roles bundle permissions; code checks the permission.
   - **Roles are scoped per organization/workspace, not global.** Multi-tenant apps: verify a join table scopes role to tenant, and that the active tenant comes from a validated claim, not a client-supplied header trusted as-is. Test by acting as an admin of Org A against Org B's resources.
   - **The API server's database credential is subject to RLS.** Request-path connections use a non-superuser role; `BYPASSRLS` credentials and Supabase `service_role` keys are confined to background workers and migrations. A service key in the request path silently neutralizes every RLS policy in the database.
   - **RLS policies define both `USING` and `WITH CHECK`.** `USING` alone filters reads but leaves inserts/updates able to write rows the user could never read back.
   - **Routes default-deny across every HTTP verb.** Authorization commonly exists on `GET /resource/:id` and is missing on `DELETE`/`PATCH` of the same resource, and unmatched-route fallbacks expose handlers with no check at all. Verify the fallback returns 403, and test each verb separately (OWASP API5:2023).
   - **Permission changes take effect promptly.** Access-token TTL short enough (≤15 min) or an active revocation check, so a revoked role does not stay live until a long-lived token expires. Verify by revoking a role mid-session and confirming the next request fails.
   - **Prompt injection mitigation on any LLM/AI surface.** User-supplied content that reaches a model prompt is fenced/delimited from the system instructions rather than concatenated in as free text; the model's own output is treated as untrusted — never eval'd, never used to gate an authz decision, never fed back into a privileged action without re-validation.
   - **AI usage caps on generation endpoints.** Per-user quotas and rate limits on any route that calls an LLM/AI model, so a single user, a bug, or a runaway agent loop can't run up unbounded provider spend.

   **Additional findings checklist (sourced 2026-08-04 from @jordankodes "Your App = AI Slop", https://www.tiktok.com/@jordankodes/video/7662150345858092302, and Tom Is Loading (@tomisloading, hover.dev) "6 ways to prevent AI slop in your frontend UIs", https://www.tiktok.com/@tomisloading/video/7623474782897540383, which references Refactoring UI, WorkOS and Stripe Dashboard as good examples).** GLM spokes must check each item explicitly rather than rely on the general anti-slop instruction above, writing hits into `ui-slop.md` same as the rest of this item:
   - **Mobile horizontal clipping**: any layout that overflows or clips horizontally on a mobile viewport is a defect, not a suggestion.
   - **Hero badge**: a small pill/badge (e.g. "EARLY ACCESS", "AI-Powered X") placed directly above a hero H1, independent of whether a 3-card grid follows.
   - **Footer legal links**: a production footer with only a copyright line and no Terms of Service or Privacy Policy links.
   - **Card overuse**: boxing every section in a bordered or shadowed card when spacing and type hierarchy alone would separate the content.
   - **Progressive disclosure**: dashboards and tables exposing every action at top level (per-row view/copy/delete buttons, redundant columns) instead of hiding secondary actions behind a menu.
   - **Excessive borders**: borders drawn between nearly every element instead of spacing; borders everywhere signal a missing hierarchy.
   - **Color discipline**: many vibrant colors mixed at once (multi-color tab headers, rainbow status badges, multi-color gradient cards) instead of a neutral layout with one primary accent reserved for the main CTA.
   - **Pill tabs as primary nav**: inset/pill-style tab components (the default shadcn/ui `<Tabs>`) used as top-level page navigation, instead of reserved for supplemental or toggle state, with underline-variant tabs or a sidebar used for primary nav.

   **More findings checklist (sourced 2026-08-09 from Hayden Schmitt, @haydenschmitty, "what separates a vibe-coded app from a designed one", https://www.tiktok.com/@haydenschmitty/video/7671140138939960590).** Same framing: GLM spokes must check each item explicitly rather than rely on the general anti-slop instruction above, writing hits into `ui-slop.md` same as the rest of this item. His claim is that the difference between a vibe-coded app and a designed one is not a new tool or component library but a handful of interface patterns plus removing the tells AI generators leave behind. These come from short-form video and are checklist material, not a design system, so treat them as audit checks rather than a prescription to rebuild the UI:
   - **Skeleton loaders, only where an unexplained wait exists.** Grey placeholders shaped like the layout that is about to load, instead of a spinner or empty space, reduce perceived latency and prevent layout shift. The check is "is there an unexplained wait", not "does every async thing have a skeleton": a fast fetch, a real percentage-progress bar, or a button that morphs into its own pending state are already correct, and adding skeletons there is over-engineering. Cross-reference item 7 (ponytail) rather than flagging that case as a slop hit.
   - **Semantic state colours.** State maps to colour the way users expect: green success, red danger, amber warning, blue or neutral informational. The specific finding to hunt is an app that has brand and section colours but no state palette, and therefore signals errors and destructive actions by borrowing an unrelated accent. Destructive actions must read as destructive at rest, not only on hover.
   - **Remove the explainer sub-paragraph (per heading, not per page).** His tell: AI generators "love to put these subheader pieces of text under everything". If a heading is self-explanatory, the sentence under it restating what the heading means is noise and pushes the functional part of the page down. The rule he gives is "if it is not tangibly useful, remove it". The audit check is per heading, not per page. (Overlaps the existing "Redundant subheadings" bullet above; check both, do not double-count.)
   - **Accessibility auditing, cross-referenced not duplicated.** He calls this "far and away the most common issue I run into" and frames it as legal exposure, not polish. This overlaps the queue's existing item 8 (WCAG): a UI-anti-slop pass that finds contrast or keyboard problems should hand them to item 8 rather than fixing them in isolation, so record a pointer in `ui-slop.md` and let item 8 own the fix.

Same short-form-video caveat as the block above: checklist material, not a forms library:

Rules:
- **Loop-until-clean on every APPLICABLE item (0-16), not just one fix pass** (an item or group the Step 0 profile marked `N/A` has no loop to run and is not revisited). Find → verify → fix → test is not "done" the first time it returns clean-looking output: after applying fixes, RE-RUN that same item's find/audit step again on the same scope. Only move to the next item once a full pass returns zero new findings. If a fix pass introduces or surfaces a new issue, that's still the same item's loop, not a new item. This applies uniformly to item 0's idea pressure-test (loop until STRONG or user-directed pivot) exactly as it does to bugs/security/WCAG/etc. (loop until a clean audit pass finds nothing).
- **Engine = GLM hub-spoke, NOT ultracode.** Volume (find / fix / test) → `glm-code` spokes. External facts → agy `/research`. The Claude hub ONLY plans, writes specs, reviews diffs, and runs gates. This is deliberate: it conserves Claude quota and uses the flat-rate GLM plan for the heavy lifting.
- **Quota discipline (now GLM-driven):** run `~/.claude/orchestrator/state/glm-usage.sh` before every wave. ≥70% → prefer glm-4.7 and halve wave sizes; ≥90% → STOP until reset. Honor the GLM peak-hour deferral (06:00–09:59 UTC).
- Reported findings files (`bugs.md`, `secure.md`, `minimap`) must be written BEFORE their fixes are applied, per each item's wording; keep the minimap and audit bookkeeping files gitignored where the item says so.
- Verify fixes with real test / gate runs the hub executes — evidence before "done" on every item; a spoke's ✅ is a claim, not proof.
- Long run: apply the Limit Looping usage checks from CLAUDE.md throughout (usage + mtime staleness + resume.md pause/resume).
- **Loop-until-clean and every gate decision are measured against the Step 0 profile, not against this document's full length.** A check the profile marked `N/A` is not a gap, a finding, a debt item or a TODO — it is a check this project does not need at its current shape.
- Finish with a summary: per-item outcome, findings counts (verified vs refuted), fixes applied, gates status, and GLM/Claude spend. Include a **dynamic vibecode-security score — `passes / APPLICABLE`, never a fixed denominator** (the old fixed `/37` is retired as of 2026-08-04; it double-counted checks that a given project could never trigger). The candidate pool is one point per check in item 2's backend-reachability checklist plus rate limiting, auth on protected routes, dependency-CVE cleanliness, billing/cost alerts, and automated backups — but **the denominator is only those the profile marked APPLICABLE**. Skipped checks leave BOTH halves of the fraction and are listed separately as `N/A — <trigger absent>`. **Print the profile and the applicable count on the same line as the score** (e.g. `18/18 — local-only, single-operator, no auth, no personal data, no money; 19 checks N/A`), so a fully-clean small-project audit is never read as weaker than a `30/37`. No scoring machinery, just count the passes. Floor rule, restated for the dynamic score: any FAIL in the ALWAYS-ON floor, or missing more than a quarter of the applicable checks, means the security work isn't done regardless of what the other items say — it marks "dangerously broken", not a pass mark.
- **No manufactured work.** The audit reports what this project actually needs at its current scale and stage — it must never recommend infrastructure, hardening, tooling or process that the Step 0 profile does not justify (no tenancy for a single-tenant app, no WAF for a localhost tool, no DPA for synthetic data, no 2FA where there are no user accounts). Item 7 (ponytail) applies to the audit's OWN recommendations: a recommendation justified only by a profile value this project doesn't have is a ponytail finding against the audit, and gets struck before the report goes out.
